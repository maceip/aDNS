## Governed recovery after replacement

This is an initial-admission `Join` configuration with a static predecessor target. It is not a safe sole-node reboot configuration. CCF 7.0.15 creates a new identity after process loss; a sole remaining authority must follow its existing governed `Recover` procedure. Do not use Azure's generic restart operation as a recovery test.

After a successful replacement, recovery uses the successor's own `ccf-join-20260921-v3` ledger/snapshot state, with no concurrent writer, and the then-current service CA as `previous_service_identity_file`. It must not reuse the stale `472b…` previous identity from the old deployment. The existing active recovery participant and encryption key satisfy the current threshold of one; verify that status again before any fault injection. Authenticate the Recover node's exact native policy, acknowledge governance state, govern `transition_service_to_open` with the exact previous and newly generated service certificates, and submit the participant's decrypted share through the existing signed recovery endpoint. Keep decrypted material in memory.

CCF Recover creates a new service CA even when DNSSEC keys, TSIG keys and committed data are preserved. Coordinate all service-identity and node-policy pins and repeat native renewal, receipt, DNSSEC and transfer checks before claiming recovery complete. Historical restoration evidence remains unchanged. The read-only predecessor snapshot mount is an initial Join input; subsequent recovery is based on the successor's own durable state.

The retained [local consensus proof](../../../../docs/evidence/azure-join-v3-20260921/local-join-proof.json) used the exact deployed CCF binary with a deliberately unreachable old consensus address, disabled snapshot RPC, and read-only snapshot bootstrap. It proves protocol behavior in Virtual mode, not native admission or successful production cutover.
