# Pinned CCF integration

The production adapter builds against CCF **7.0.15** on Azure Linux 3, using the release RPM and base image digests pinned in `containers/ccf-toolchain.Dockerfile`. `containers/agentdns-ccf.Dockerfile` produces the standalone CCF 7 executable plus the autonomous host driver. Pin the resulting OCI digest in the confidential deployment policy; a mutable tag is not an attestation identity.

The SDK's `UserEndpointRegistry` is dispatched by CCF's fixed `app` actor. Native paths therefore use `/app/service/...` (including `/app/service/anchor`), `/app/zone/...`, `/app/governance/ksk-receipt`, `/app/governance/policy-receipt`, `/app/governance/anchors`, and `/app/dns-query`. An approved TLS frontend can map the specification's unprefixed paths to these native routes. The request signature binds the service audience and action, so that mapping does not alter signed content.

## Transaction and key boundaries

`adns-ccf` borrows one live CCF transaction through a noncopyable opaque `cxx` wrapper. It never retains C++ slices or transaction handles after a handler returns. Consolidated table names are fixed in the C++ bridge. Private DNSSEC keys and TSIG secrets use `agentdns.private_keys` and `agentdns.tsig_secrets`, without the `public:` prefix. No API exports either secret collection.

Every successful response, including read-only snapshots, passes through `set_consensus_committed_function`. Read handlers must finalise their empty write set: CCF 7 bypasses the callback entirely if `set_apply_writes(false)` is used. Rejected application writes are discarded by an overlay. Only explicitly authenticated nonce-bound rejection metadata (and its monotonic clock watermark) may commit on an HTTP4xx, through the same global gate; internal errors discard the entire backend transaction. Pending/failed execution observations remain distinct from commitment of the observation snapshot, as specified in [request-reconciliation.md](request-reconciliation.md). A successful callback checks `FinalTxStatus::Committed`; reconciliation captures the original stored result's view during endpoint execution and verifies it is an ancestor of that committed snapshot. Delayed callbacks run under CCF's Raft lock, so they must not call consensus accessors that reacquire that lock. The adapter adds `x-agentdns-commit-status: committed` only then. Frontend propagation remains pending until a signed secondary response is accepted.

The callback also gates raw TCP AXFR/IXFR frames, UDP SOA answers, DoH and signed outbound NOTIFY/SOA work. CCF 7's response gate requires HTTP1, so the adapter refuses service if any configured interface enables HTTP2. The internal interface must be named `agentdns-internal`, bind loopback, and receive the request directly. Internal routes never forward to another replica and cannot be called through the public interface.

The host driver holds no DNSSEC or TSIG secret. Governance pins each secondary's key name, numeric endpoint, zone scope and SHA-256 secret digest. The internal provisioning endpoint only installs an absent key whose value matches that approved digest; an exact restart retry acknowledges the existing matching value without rewriting it. Changing a secret or endpoint requires a new governed key identity. Every transfer, outbound request and accepted secondary response rechecks current governance. Signed work is persisted before delivery and responses are bound to the exact outstanding request, endpoint, TSIG request MAC, DNS ID, question and expiry. Work batches contain at most 256 items and rotate using a durable cursor, preventing early peers from starving later peers. Governance caps transfer identities at 512 and zones per identity at 128.

KSK receipts use CCF's genuine `build_receipt_for_committed_tx` and `describe_receipt_v1` proof. The transaction claim binds the complete canonical owner and DNSKEY RDATA. A durable receipt counter ensures a real ledger leaf even when the KSK has not changed. `tools/verify_ksk_receipt.py` independently checks the claim, DS, node endorsement, Merkle proof, signature, transaction ID and externally supplied service identity.

The supervisor validates the running node's TLS identity before starting its pinned driver and restarts that driver if recovery replaces the service certificate. Member private keys are not packaged or needed by the node; initial configuration contains member public certificates and encryption public keys.

Production startup supplies `--config-manifest /config/manifest.json --config-manifest-sha256 <digest>`, with that exact command pinned by the confidential container policy. The strict manifest maps absolute file paths to SHA-256 digests and covers `node.json`, each referenced constitution/member certificate/encryption key/member data file, and optional node/service data files. The supervisor verifies bounded regular inputs and freezes their bytes into a private bootstrap directory before launching CCF. Pinning only a mounted volume does not bind its initial contents. Runtime hardware endorsement files retain CCF's own cryptographic validation and are not added to the bootstrap manifest.

An optional `--provision-tsig-file /config/transfer-key.json` reads `{key_name,secret_base64url,zones}` from a confidential secret volume. Read-only ACI files (0444/0644) are accepted, group/other writable files and symlinks are rejected, and no input is logged. The supervisor retries only while governance is not ready or transport is unavailable, and records success only after global commitment. CCF and the secret-free driver inherit only essential locale/path variables plus `UVM_SECURITY_CONTEXT_DIR`; deployment credentials and arbitrary secret environment variables cannot enter CCF's startup environment log.

Governance configuration changes are staged as `governance/configuration` and installed by the Rust maintenance transaction before zone initialisation. The epoch must advance; the applied time watermark is the maximum of current live time and the proposed value, so a stale governance mirror cannot regress time. Authority state has versioned active indexes and explicit bounds documented in `docs/lifecycle-bounds.md`.

Before signing, the complete snapshot combines governed base records and owned contributions. Every `(canonical owner, type, class)` RRset uses the minimum TTL among all of its source records, then canonical duplicate records are removed. Stored base records, contributor identities and original TTLs remain intact: withdrawing a lower-TTL contribution restores the remaining source TTL. A base TXT record at TTL60 and an operator TXT record at TTL300 therefore publish as one valid TTL60 RRset. Different CNAME targets and CNAME/other-data conflicts reject all application effects and preserve the nonce; an eligible HTTP4xx may retain only the diagnostic observation described above. Regression tests verify actual RRSIGs, both TTL directions, duplicate base records and ownership after signed deletion.

## Reproduce the local CCF tests

```sh
docker build --platform linux/amd64 -f containers/ccf-toolchain.Dockerfile -t agentdns-ccf-toolchain:7.0.15 .
docker run --rm --platform linux/amd64 \
  -v "$PWD:/src:ro" -v agentdns-ccf-build:/build -v agentdns-ccf-cargo:/root/.cargo \
  agentdns-ccf-toolchain:7.0.15 sh -c \
  'cmake -S /src/ccf -B /build -GNinja -DCMAKE_BUILD_TYPE=Release && cmake --build /build -j4 && python3 /src/ccf/tests/live_smoke.py'
docker build --platform linux/amd64 -f containers/agentdns-ccf.Dockerfile -t agentdns-ccf:7.0.15 .
```

The smoke test creates a real CCF network, opens governance, installs an Owner Grant, initialises a zone, submits a genuinely signed operator action and verifies original transaction reconciliation. It checks public/internal interface isolation, content types, genuine KSK receipts and tampered owner/RDATA/proof/transaction negatives, and both DoH methods. Public evidence is in `docs/evidence/ccf`; member keys, node state and the private ledger remain in the test volume and are not exported.

`python3 /src/ccf/tests/live_smoke.py --quorum` additionally creates two governed peers for consensus failure testing. Test network relays close replica links before the peers pause, so tentative writes cannot remain buffered in peer sockets. Ten response paths, including authenticated failed submissions and their observation reads, remain withheld during quorum loss, resume only on commit, and a lost primary's tentative success and failure metadata leave no result or consumed nonce. The surviving committed nonce reconciles as pending. KSK and authenticated AXFR checks verify replicated private keys on the elected replacement.

`python3 /src/ccf/tests/live_smoke.py --recovery` separately stops the node, starts a fresh CCF `Recover` process from a complete disk ledger/snapshot copy, authorises the old/new service identity transition and decrypts/submits a real consortium member recovery share. It checks the same KSK, original TSIG key, historical request/result transaction ID, an authenticated failed observation and a pre-shutdown unconsumed nonce. Both old and new service-identity KSK receipts are independently verified. This uses governed operator records; the test does not fabricate an attested service registration.

Recovery must preserve the current `ledger_N` chunk as well as closed `.committed` chunks. A current chunk can contain globally committed entries before rotation; CCF intentionally ignores that open chunk when it appears only in `read_only_directories`. Recover a complete stopped-node copy into the new writable ledger directory. Never infer a complete backup from closed-chunk filenames alone.

Local tests set `CCF_PLATFORM_OVERRIDE=Virtual` strictly to test CCF consensus. They do not establish SNP hardware evidence or confidential deployment acceptance. Genuine Azure evidence and the hardware/container acceptance chain require the separately recorded isolated deployment test.

CCF's release static archive and the application's Rust static library each embed a complete Rust standard library. Their strong unmangled exception personality names collide at link time. `ccf/namespace_rust_runtime.py` makes an isolated SDK archive copy and consistently renames only its `rust_eh_personality` definition, corresponding `DW.ref` definition and all references. It checks the expected symbol counts; it neither permits duplicate definitions nor substitutes one toolchain's runtime for another.
